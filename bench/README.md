## 怎么跑

对拍跑在自己的镜像里（[`../docker/Dockerfile.bench`](../docker/Dockerfile.bench)），
枢衡与三家竞品同处一室。

```bash
bash tests/bench/run.sh
```

这条命令建镜像、核对钉死的版本、然后在容器里把整条流水线跑一遍并断言判据两个方向
都判得动。**它不是对拍本身**，它是「对拍这套东西还活着」的门。

真正要出数的那天，在**合格宿主**上跑**启动器**（G145）：

```bash
BENCH_HOST_ATTEST="专机 · 无 TUN 代理" \
BENCH_SERVER_CPUS=0-1 BENCH_LOAD_CPUS=2-3 \
BENCH_DURATION=60s BENCH_CONNECTIONS=200 BENCH_WORKERS=2 \
BENCH_FULCRUM_BIN=/path/to/fulcrum \
  bash bench/docker-run.sh bench/out
```

★ ★ **⛔ 不要直接 `bash bench/run.sh`**（那是容器内那一步）。启动器做三件容器
自己做不到的事：在**宿主上**判 `net.core.netdev_max_backlog`（不符就拒绝启动）、
把另外四个键作为 `--sysctl` 旗标带进容器、把宿主实测值经环境变量传进去。
⇒ 绕过它起容器，快照拿不到那个凭证，**这一趟会被判成不合格** —— 那是有意的。

五步，顺序是承重的：**① 判据自测 → ② 环境快照与合格性 → ③ 逐类跑（只产原始数据）
→ ③′ 诊断读数 → ④ 判定**。①排最前的理由：判据坏掉最典型的形态是**它恒返回同一个答案**，
而那种坏法在后三步里长得和一切正常一模一样。
★ ③′ 见下面「**诊断读数（⛔ 不是 §8 的一类）**」那一节 —— 它**不参与 ④**，
且它的失败**有意不中止 ④**：④ 是 §8 的结论，让一个诊断步骤把它扣掉，
在合格宿主的窗口里意味着白停一次服。

## 合格宿主

判据在 [`lib.sh`](lib.sh) 的 `bench_disqualifiers`，写成**纯函数** ——
读数由调用方传进来，⇒ 两个方向都能用合成输入当场证给人看
（`bash bench/lib.sh --self-check`）。**一条理由都打不出来 = 合格。**

**六条**，分成性质完全不同的三半（★ G145 把「内核参数」那一条从人写的声明里拆了出来）：

### 容器自己看得见的（机器判）

| 判据 | 不合格的形态 | 为什么 |
|---|---|---|
| `kernel` | 内核串里带 `microsoft` / `wsl` | Docker Desktop 的 Linux 侧跑在 WSL2 里。G132 记的实测理由是这台开发机上那个 TUN 代理**会干扰网络**（容器出不去 UDP/443）⇒ 这是唯一一条不需要人配合就判得死的证据 |
| `cpus` | 核数少于 `BENCH_MIN_CPUS`（缺省 4） | 负载生成器与被测**不许共享 CPU**，分不出两组就谈不上 |
| `load` | 1 分钟负载高于 `BENCH_MAX_IDLE_LOAD`（缺省 0.50） | 机器在干别的活，等于被测在与别人共享 CPU |
| `affinity` | 没有**同时**给 `BENCH_SERVER_CPUS` 与 `BENCH_LOAD_CPUS` | §9 的缓解项逐字写着基准环境要固化**内核参数与 CPU 亲和**。⚠ 只给一个等于没给 |

⚠ `affinity` 判的是「有没有钉到不相交的核上」，⛔ **不是**「钉得对不对」——
后者要看具体机器的拓扑，而那台机器今天不存在。

### 内核参数与资源上限（`kernel-params`，**G145 起是门，不再是声明**）

★ ★ ★ 这一格此前是下面那句人写的声明里的第三件。2026-09-06 的实测把那条路整个
否掉了 —— 两个方向都量过：

| 在宿主上设 | 新开的默认网络容器读到 |
|---|---|
| `net.ipv4.ip_local_port_range = 20000 60000` | 仍是 `32768 60999` |
| `net.core.somaxconn = 12345` | 仍是 `4096` |

那四个键是 **per-netns** 的，而对拍整个跑在自己 netns 的容器里
⇒ **一句完全诚实的「已固化」声明，对被测行为零影响**。
⚠ 这正是本仓最在意的那一族：一道恒绿的门与一道不存在的门，输出完全一样。

⇒ 六个键按「设得进哪里」重新分了三处，**每一处都有门**：

| | 键 | 在哪里设 | 谁判 |
|---|---|---|---|
| 容器侧 | `net.core.somaxconn` = 65535 · `net.ipv4.tcp_max_syn_backlog` = 65535 · `net.ipv4.ip_local_port_range` = `10240 65535` · `net.ipv4.tcp_tw_reuse` = **2** | `docker run --sysctl`（由 `bench/docker-run.sh` 从 `bench_container_sysctls` 推导）| `env-snapshot.sh` 在容器内逐条断言「实测==声明」|
| 宿主侧 | `net.core.netdev_max_backlog` = 16384 | `bench/sysctl.conf` → `/etc/sysctl.d/` | `bench/docker-run.sh` 在**宿主上**直读 `/proc/sys`，不符**拒绝启动** |
| 资源上限 | `nofile` = 1048576 | `docker run --ulimit` | `env-snapshot.sh` 核 `ulimit -n` |

- ⚠ `netdev_max_backlog` **设不进也读不到**容器（runc 当场拒绝；容器里 `/proc/sys/net/core/`
  下没有这个文件）⇒ 它只能宿主判，而启动器把宿主实测值经 `BENCH_HOST_SYSCTLS` 传进容器。
  ★ 绕过启动器手起容器 ⇒ 拿不到那个凭证 ⇒ **判成不合格**。
- ⚠ `tcp_tw_reuse` 声明成 **2 而不是 1**：`2` 的语义是「仅对环回启用」，而四家与 oha
  同处一个容器、只走环回 ⇒ 2 恰好覆盖本场景，1（全局）更宽却**不更贴切**。
- ⚠ ⚠ **`fs.file-max` 已从清单中移除**。★ 实测那台候选宿主上它是 `9223372036854775807`，
  而此前 `sysctl.conf` 里写的 `2097152` 是把它**往下压**。真正会咬的是每进程的
  `RLIMIT_NOFILE` —— ★ **实测容器缺省只有 1024**。⇒ 改设 `--ulimit nofile`。
- ★ `bench/sysctl.conf` 仍写明**有意不放进来的三类**（拥塞控制 · socket 缓冲 · `vm.*`）——
  它们会**改变结论本身**，而不只是消除噪声。

★ **这道门在每一次 `tests/bench/run.sh` 里两个方向都被走到**：门禁**有意不设**
`BENCH_HOST_SYSCTLS` ⇒ 容器侧四个键因旗标真的生效而**相符**（C13，正向），
宿主侧那一条因缺凭证而**判红**（C12，反向）。⛔ 别为了让输出好看去补那个变量。

### 容器原理上看不见的（要人声明：`BENCH_HOST_ATTEST`）

容器无从知道这台机器是不是在跑真业务、网络路径上有没有代理。⇒ 这两件只能由人写下来：

1. **这是专机** —— 没有在承载任何真业务（生产机不算合格宿主，它会与被测抢 CPU）
2. **网络路径上没有 TUN 代理 / VPN**

★ ★ **声明不是证明。** 这一格能做到的只有「谁都没声明过就一定不算合格」，
⛔ 它拦不住一句不实的声明 —— 那一格没有门，只有纪律。快照会把声明原文记下来。
⚠ **声明原文要如实**：这台机器上如果还有任何东西在跑（云厂商探针、隧道客户端），
⛔ 不是装作没有 —— 照实写进那句话里。

## 判定口径

判定在 [`verdict.sh`](verdict.sh)，它**先问宿主合不合格**：

- **不合格** ⇒ 逐条说出理由，写 `VERDICT: UNQUALIFIED`，然后停下 ——
  不取最强者、不算门槛、不打 PASS / FAIL。原始数据仍然完整落盘，
  ⚠ ⛔ 那份数据证明的是**流水线跑得通**，它不是、也不许被引用成性能读数。
- **合格** ⇒ 逐类判：

  ```
  该类最强者 = max(三家竞品在这一类的读数)      ⛔ 不是三家平均，⛔ 不是钉死某一家
  门槛       = 最强者 × 0.9                     （G19「不劣于 10%」，含等号）
  PASS       ⟺ 枢衡 ≥ 门槛
  ```

★ **「最强者」逐类现算。** §8 写着静态那一类比的是 nginx、L4 那一类比的是 HAProxy ——
枢衡要在**每一格**追上那一格的冠军。⛔ 跨类取最强者是错的。

⚠ 竞品集合是「除枢衡以外的全部」，**推导出来而不是写死的名单** ——
写死的名单在加第四家时没人会想起来去改，而它安静地少比一家。

⚠ ⚠ **方向今天只处理「越大越好」那一种。** 延迟类是反过来的；加第二类时要
显式给方向参数，⛔ 不许让判据去猜。

### 读数什么时候不算数

一份跑得飞快的 5xx 会给出非常好看的 `requestsPerSec`。⇒ [`read-raw.py`](read-raw.py)
在比较**之前**先校验每一份原始数据：`successRate` 必须**恰好** 1.0 ·
状态码分布里**只有** 200（⛔ 判「只有」不是判「有」）· 传输层错误为空。
任何一份不合格 ⇒ 这一类报 `NO-VERDICT`，⛔ 它不会被当成一个数悄悄排进去。

★ 用例脚本在**开跑前**还核过一次（状态码 + 字节数逐字节对）。两次核的不是同一段
时间：一次防「一开始就没在服务那个资源」，一次防「负载期间中途变坏」。

### ★★★ 压测端自己先饱和 ⇒ 这一类作废（判据 ④）

上面那几条守的都是**单份读数**坏掉。还有一种坏法，每一份读数都完美合格：
**负载生成器自己先到顶了。** 那时四家会一起收敛到 oha 的天花板，而
「不劣于最强者 10%」这条**照常打 PASS** —— 输出一组看起来完全正常、
其实量的是 oha 的数。⚠ 合格宿主那六条一条都答不了它：它们判的是这台机器合不合格，
而这里坏掉的是**量具本身到顶了**。

两条判据，性质完全不同：

| | 判什么 | 阈值 | 今天的地位 |
|---|---|---|---|
| **B 收敛** | 全场读数彼此挤在一起（`(最高−最低)/最高` 低于阈值）| `BENCH_MIN_SPREAD`（缺省 **0.05**）| ★ **承重**。不需要任何新测量，用已采到的那组数 |
| **A 绝对天花板** | 最强者越过「生成器上限 × headroom」| `BENCH_GEN_HEADROOM`（缺省 **0.90**）| ⏳ **可选**。要 `raw/<类>/ceiling.txt` 里有个数，没有就整条不参与 |

B 的依据：nginx（C）· HAProxy（C）· Caddy（Go）· 枢衡（Rust/pingora）是四套结构
完全不同的实现，它们落进同一个百分点里，**「共享了某个外部上限」远比「它们真的
一样快」更可能**。⚠ 它说不出是哪一个上限（生成器 / 环回 / 亲和）——
⛔ 别把它读成「一定是 oha 饱和了」，它只说**这组数不可比**。

⚠ ⚠ **A 今天有意不是承重件**：它的正确性整个压在「参照服务真的比四家都快」这一条上，
而那条在合格宿主到位之前**验不了** —— 参照选慢了就恒作废，选的是另一个真实服务器
则量到的是 `min(oha, 那个服务器)`，天花板被低估。⇒ 参照服务选定那天再打开它。
⛔ ⚠ 那个文件**不许叫 `ceiling.json`**：`read-raw.py` 对该目录做 `glob("*.json")`，
一个 `.json` 会被当成第五家被测混进竞品集合，而那不会有任何东西说。

### ★★★ 2026-09-06：第一趟真实数据之后，这两个阈值的回核

原文写的是「`0.05` 与 `0.90` 没有实测支撑，它们是判断不是读数，**第一次在合格宿主上
跑完之后要回头核**」。跑完了，回核结论如下。

**`BENCH_MIN_SPREAD = 0.05`：这一趟没误报，但暴露了 B 的一个真实缺陷。**

| | |
|---|---|
| 全场 spread `(最高−最低)/最高` | **0.8599** ⇒ 远高于 0.05，不作废 ✔ |
| ⚠ ★ 最快两家 haproxy vs nginx | **0.0071** —— **低于 0.05** |

⚠ ⚠ ★ **两套结构完全不同的实现（C 写的 nginx 与 C 写的 HAProxy，架构差异极大）
落进 0.71% 以内，正是 B 声称要怀疑的形状 —— 而 B 一声没吭。**
原因在判据的形状里：B 取的是**全场极差**，而枢衡的慢（0.86）把它整个撑开了。
⇒ **一个慢的被测会掩盖掉快的那几家之间的收敛。**

★ 这条是第一组真实数据给出的、可以推翻原设计的证据 —— 正是「回头核」要的东西。
✅ **已由 `G146` 结案**（原 `D34`）：新增判据 **④C `bench_top_convergence`**，
判「最强者 vs 第二强」，⚠ ⚠ ★ **只作用于 PASS，永远不作用于 FAIL**：

> 门槛 = `max(竞品) × 0.9`。那个 max 被外部上限压住时，**门槛是被低估的**。
> · 结论是 **PASS** ⇒ 枢衡可能只是压过了一个被低估的门槛 ⇒ 不可信，**作废**。
> · 结论是 **FAIL** ⇒ 真实门槛只会**更高** ⇒ FAIL **更成立** ⇒ ⛔ **不该作废**。

★ `G142` 那条「两边都往作废侧倒」的初衷是**不给出错结论**，而天花板之下的 FAIL
不可能是错的 ⇒ 这不是放松。⛔ 三条原候选（最快 k 家 / 每一对 / 极差外加一条）
都会把 2026-09-06 那个结实的 FAIL 扣掉 —— 而那**不是推理，是量出来的**：
反证里把判据改成「作用于所有结论」（就是那三条的形状），C15 那个 FAIL 当场变成 VOID。

⚠ ⚠ ⛔ **`0.05` 这个数本身仍然没有实测支撑** —— G146 改的是「拿它去比什么」，
**不是「它该取多少」**。⛔ 别把这一条读成「阈值已被实测确认」。

**`BENCH_GEN_HEADROOM = 0.90`：仍然验不了。**

A 这一趟没打开（没有 `ceiling.txt`）⇒ 这个数**一次都没被执行过**。
⚠ 而这一趟恰恰给出了「为什么需要 A」的第一个真实理由：haproxy/nginx 收敛在
~54.5k，**与「oha 在 2 个核上到顶」的形状一致**，而本套东西证不了它们不是撞到了
量具的天花板。⇒ 选定参照服务那天再回来。

★ 误判方向是**有意不对称**的：一次误作废只是**扣下一个结论**，一次漏判是**给出一个
错结论** ⇒ 两条都往「作废」那侧倒，且**「判不了」（有效读数不足两条 / 上限不是正数）
一律作废，⛔ 不算通过**。判定报 `VOID`。

## 四家怎么摆平

配置模板在 [`conf/`](conf/)，是交付物的一部分 —— 第三方要看的就是那四份配置本身。

| 对齐项 | 口径 |
|---|---|
| **一次只起一家** | 四家同时跑会互相抢 CPU，量到的是「四家一起跑」这件事 |
| **同一个 payload** | 固定字节数（缺省 4096），同一个 URL 路径。★ 用随机字节而不是可压缩的重复字节：**不比压缩**。⚠ ⚠ **两类取的不是同一份字节**：静态吞吐用 `/dev/urandom`，反代吞吐用 base64 字母表（源站的 `respond` 正文**只有内联形态**，必须可打印）⇒ ⛔ 两类的绝对读数不可并排比较 |
| **访问日志全关** | 日志是另一件事，开着会把它的代价算进吞吐 |
| **明文 HTTP/1.1 + keep-alive** | TLS 归「TLS 握手」那一类，⛔ 不混进来 |
| **上游连接复用** | ★ 只对**有上游**的类（今天是反代吞吐）。四家的**默认**行为不同，而 **oha 的 JSON 里看不出这件事** ⇒ 四家全部显式配置；逐家的理由写在各自的 [`conf/`](conf/) 模板里。由判据 ⑤ 判着，见「§8 的类」那一节 |
| **权限身份一致** | 四家在容器里都是 root。⚠ nginx 因此要显式 `user root`（只搬二进制搬不到官方镜像里那个系统用户），⛔ 不许改成只给它降权 —— 降权本身对吞吐有代价 |
| **worker 数一致** | `BENCH_WORKERS`，**缺省 1**，见下 |
| **站点根的文件系统** | `BENCH_WWW_ROOT`，缺省是启动器挂的一个**匿名卷（ext4）**，见下 |

⚠ ⚠ ★ **上面这几个缺省只在 [`lib.sh`](lib.sh) 的「负载参数」一节定义一次**，
用例脚本与 `env-snapshot.sh` 都从那里取 ⇒ **`env.json` 的 `load_params` 四格
必然说得出这一趟真的用了什么**。
⛔ **别在用例脚本里再写一份 `:-` 缺省**：2026-09-06 之前正是那样 —— 用例用
「声明值**或缺省**」而快照记「声明值」，于是没人显式设的参数，
**用例真的用了缺省而快照写 `null`**。那一趟的 `payload_bytes` 就是这么丢的
（门禁里 `workers` 同时也是 `null`）。
★ 这一格现在由 `tests/bench/gate.sh` 的 **C16** 守着（判 A 那一趟**真跑出来的**
快照，⛔ 不是合成夹具）。

### ★★★ 站点根落在哪种文件系统上 —— 它是口径，⛔ 不是编排细节

枢衡的静态文件路径先在**本线程**上试一次 `open` + `fstat` +
`preadv2(RWF_NOWAIT)`，读全了就整趟零跨线程；只有内核说「这一次要等」才付一次
`spawn_blocking`。⚠ ⚠ ★ 而 **`RWF_NOWAIT` 是每个文件系统各自决定认不认的**。

2026-09-06 在内核 `6.18` 上实测：

| 文件系统 | 4096 字节热文件上的 `preadv2(RWF_NOWAIT)` |
|---|---|
| **ext4** | **读全了** |
| overlayfs | `EOPNOTSUPP` |
| tmpfs | `EOPNOTSUPP` |

⇒ **同一个二进制、同一份配置、同一台机器，站点根换一种文件系统，
静态吞吐差 45%**（诊断台实测 28.6k → 44.4k rps）。

⚠ ⚠ **在 2026-09-06 之前，站点根来自 `mktemp -d`，落在容器可写层（overlayfs）上**
—— 那是编排的副产品，**从来没人挑过**，却决定了被测的哪条路径会被走到。
⇒ 现在 [`docker-run.sh`](docker-run.sh) 挂一个**匿名卷**（`-v /bench-www`，
`--rm` 会连它一起删）并把 `BENCH_WWW_ROOT` 指过去，理由是**枢衡按 G13 的分发形状
（systemd + 单静态二进制）在生产上的站点根就在 ext4/xfs 上**。

⛔ 这**不是**给枢衡开的小灶：另外三家从同一个目录读同一份 payload，
换的仍然只有被测的那一家。⚠ 但它确实**换掉了一个口径维度**
⇒ **2026-09-06 那组读数与此后的读数在这一格上不同**，⛔ 不许直接并排比较。

★ 两种形状都量得了：显式传一个空的 `BENCH_WWW_ROOT` 就回到 overlayfs。
而**不管走哪条，[`env-snapshot.sh`](env-snapshot.sh) 都把实测结果写进
`env.json` 的 `site_root`**（`path` / `fs` / `rwf_nowait`，由
[`site-root-probe.py`](site-root-probe.py) 探出来）⇒ 每一份原始数据都说得出
自己是在哪种形状下量的。
⚠ **那两个字段要一起读**：一个恒返回 `no` 的探测与「真的跑在 overlayfs 上」输出
完全相同 ⇒ `fs=ext4` 配 `rwf_nowait=no` 是一个看得出来不对劲的组合。
⛔ `unknown` 是「探不了」，**不是**「不认」。

### ★ worker 数：四家各自的旋钮，以及第一刀是怎么撞出一个缺陷的

| 被测 | 旋钮 |
|---|---|
| 枢衡 | `threads_l7`（全局块）|
| nginx | `worker_processes` |
| HAProxy | `nbthread` |
| Caddy | `GOMAXPROCS`（Go，没有 worker 进程的概念）|

⚠ ⚠ ★ **枢衡那一格是这一刀跑通之后才有的。** 2026-09-05 之前它走 pingora
`ServerConf::default()`（`threads: 1`），DSL 与 CLI 都没有调它的口子 ⇒ 四家当时
**唯一可对齐的值只有 1**。那条缺陷（D33）由 **G140** 结案：线程数按 service 角色定缺省
（L7 = CPU 核数 · L4 = 2 · 管理面与后台 = 1），三格都可被配置覆盖。

★ 这是「第一刀的价值在于把整条流水线真的跑一遍」的活样本 ——
**那个缺的旋钮不是想出来的，是撞出来的。**

`BENCH_WORKERS` 缺省仍取 **1**：它与机器无关 ⇒ 门禁里那一趟在任何机器上读数一致。
⛔ **真要出数那天必须显式设它**（按那台合格宿主的 CPU 分配）——
「四家都跑各自的缺省」与「四家跑同一个 worker 数」是两个不同的实验，
⚠ 而它们的差别在报告里看不出来，除非环境快照里那个数被读到。

### ⚠ HAProxy 在「静态吞吐」这一类里做的事更少

HAProxy **不是文件服务器**。它靠 `http-request return ... file <路径>` 回一个固定
body —— 那是它能做到的最接近「服务一个静态资源」的事，但它**不做目录、不做条件
请求、不做 range**。

⇒ 这一类量的是「把同一个固定 body 推出去有多快」，而 §8 的「静态吞吐」正是这个意思。
⚠ ⚠ **但这条口径不许在引用数字时被丢掉**：它少做了几件事，
⇒ 若它在这一类领先，那个领先里有一部分来自它没做的那几件。

## §8 的类（今天两类，还缺五类）

`bench/case/` 下每个脚本是 §8 七类里的一类，读数落 `raw/<类名>/`，
**参与最强者、门槛与 `PASS` / `FAIL`**。

| 类 | 形状 | 状态 |
|---|---|---|
| [`case/static-throughput.sh`](case/static-throughput.sh) | 四家各服务同一个固定资源 | ✅ 已在合格宿主出过数（`FAIL`）|
| [`case/reverse-proxy-throughput.sh`](case/reverse-proxy-throughput.sh) | 四家各作反代，转发到**同一个常驻源站** | ⏳ 脚本与判据就绪，**一个数字都还没有** |

⏳ 还缺五类：TLS 握手 · L4 转发 · 缓存命中 · 长连接 · 高并发短连接。
⚠ 已知它们**难度不均匀**：L4 转发撞「Caddy 官方二进制不含 L4 支持」（要 caddy-l4
插件重新构建 ⇒ 撞 **G36**）；缓存命中撞「HAProxy 没有缓存层」——
两者都自带一个「缺一家竞品怎么判」的问题。

★ `run.sh` 与 `verdict.sh` 两处都是**推导**的（`case/*.sh` 与 `raw/*/`）
⇒ 放一个脚本进 `case/` 就自动被跑到、被判到，两个文件一行都不用改。

### 反代吞吐：源站是**枢衡自己的 `respond`**，而这是个有代价的选择

一个**常驻**源站（跨四趟不重起 —— 它是环境不是被测），四家反代背靠背打它。
源站与被测**共享** `BENCH_SERVER_CPUS`：合格宿主只有 4 核，分三组会让 oha 只剩
1 核去打四万多 rps ⇒ 很可能**压测端先饱和**，而那正是判据 ④B 会作废整类的情形。

⛔ **枢衡 `file_server` 当场出局**：静态吞吐实测 7638.6 rps ⇒ 四家会一起被它压住，
判据 ④B 收敛作废整类 —— 白开一次窗口，而窗口要停一次服。

★ 镜像里能当源站的只有四家自己与 python3 ⇒ 加第五个实现要改镜像，撞 G36。
⇒ **无论选谁，都必然有一趟是「同二进制两实例」**。选枢衡的依据是**误差方向**：

> 受损的是**枢衡自己那一趟** ⇒ 若结论是 `PASS`，枢衡实际只会更强，那个 `PASS`
> 是**保守**的；⛔ 若结论是 `FAIL`，**不许拿这一条去辩解**。
> ⚠ 反过来选 haproxy 作源站，受损的是很可能的**最强者** ⇒ 门槛被低估 ⇒ `PASS`
> 不可信 —— 那正是判据 ④C（`G146`）在治的那个失效。

### ⚠ ⚠ ★ 引用这一类的数字时，三条一条都别丢

1. **枢衡那一趟是 fulcrum→fulcrum**，四家里只有它的源站与被测同二进制。
   ⛔ **不声称这个代价有多大** —— 选型那组开发机实测是个 2×2（反代 × 源站），
   而**它的对角线正好是「同二进制」格** ⇒「同二进制效应」与「源站主效应」
   **完全混杂，分离不出来**。能站住的只有定性结论：两行方向相反 ⇒ 交互作用存在，
   且对 haproxy 远大于对枢衡。
2. **源站与被测共享 server 组的核** ⇒ 这一类的**绝对读数不可与静态吞吐并排比较**。
   ★ 但源站对四家一视同仁 ⇒ 类内的相对比较（G19 那 10%）成立。
3. **payload 与静态吞吐不是同一份字节**（可打印 base64 对 `/dev/urandom`）——
   又一条「两类不可并排比较」的理由。

### 判据 ⑤：上游连接复用 —— 以及它**抓不住**什么

四家对上游连接的默认行为不同，而 **oha 的 JSON 里看不出这件事**：成功率、
状态码、错误分布全都正常，只是那一家的 rps 被系统性压低。观测量是
**每千请求新建的上游连接数**（`/proc/net/snmp` 的 `Tcp: PassiveOpens` 前后差值），
落 `raw/<类>/upstream-conns.txt`，由 `bench_upstream_reuse_violations` 判，
上限 `BENCH_UPSTREAM_REUSE_MAX`（缺省 **50**，取值依据写在 `lib.sh` 里）。

⚠ ⚠ ⛔ **`upstream-conns.txt` 有意不叫 `.json`** —— `read-raw.py` 对该目录做
`glob("*.json")`，一个 `.json` 会被当成**第五家被测**混进竞品集合。
★ 与上面 `ceiling.txt` 逐字同一条教训。

⚠ ⚠ ★ ★ ★ **它的能力边界（2026-09-09 实测，⛔ 别读成「四家都验过了」）**：

| 失效形态 | 门禁参数（2s / 10 连接） | 窗口参数（连接数大一个量级） |
|---|---|---|
| **每请求新建**（nginx 少那三行）| **1005.65** ⇒ 抓得住 | 抓得住 |
| **部分不复用**（caddy 少 transport 块）| **4.12** ⇒ ⛔ **抓不住** | 100.30 ⇒ 抓得住 |

「部分不复用」那一族的表现**依赖并发数**，而门禁只跑 10 条连接。
⇒ **同一道判据在两种参数下各抓一族**，而窗口那一趟的读数会进原始数据。
⛔ **没有为此把阈值压到 4 附近**：对齐那侧三趟实测在 0.68–3.20 之间波动（约 5 倍），
压紧会变成一道**随机翻面**的门。★ 这个盲区由 `bench_self_check` 里一条断言钉着 ——
哪天有人把阈值压紧到会误伤它，那条当场红。

## 诊断读数（⛔ 不是 §8 的一类）

`bench/diag/` 下的步骤产出的是**诊断读数**：只有枢衡自己，⛔ 没有竞品，
⛔ 不参与最强者、门槛与 `PASS` / `FAIL`。今天有两个：

| 步骤 | 量什么 | 为谁量 |
|---|---|---|
| [`diag/respond-ceiling.sh`](diag/respond-ceiling.sh) | 同一趟里 `file_server` 与 `respond` 背靠背 | 「把文件那条路修到极限能到哪」——静态文件缓存那个方案做不做由它决定 |
| [`diag/cache-hit-p99.sh`](diag/cache-hit-p99.sh) | 同一趟里**内存后端**与**磁盘后端**的命中背靠背 | `G150` ②：「磁盘命中的 p99 − 内存命中的 p99」那一格 |

⚠ ⚠ ⛔ **它的输出落 `diag/`，不落 `raw/`。** `verdict.sh` 是
`for raw_case in "$OUT_DIR"/raw/*/` —— **`raw/` 下每个子目录都会被当成一类去判**，
而 `read-raw.py` 把该目录下每个 `*.json` 当成一家被测。只有一家读数
⇒ 判据 ④ 会按「有效读数不足两条」判 `VOID`：那不是错结论，
但它把一个**诊断上界**摆成了 §8 的一个类别，而七类里没有它。
★ 与上面 `ceiling.txt` **不许叫 `.json`** 那条同族。
两个方向由 `tests/bench/gate.sh` 的 **C17** 钉着（① 两份读数真的产出；
② `bench/diag/` 下**每个脚本的名字**都不在 `raw/` 下出现）。
⚠ ★ 第 ② 半 2026-09-09 改过：它原本数的是 `raw/` 的**类别总数**（`!= 1`），
而 §8 有七类 ⇒ 补齐路上那个数要改 5 次，漏改一次要么误红、要么被人顺手放宽成不判。
⇒ 换成**推导**那份名单：加 §8 的类不用改它，加诊断步骤也不用改它。

⚠ **两处口径，引用差值时一条都别丢**：

1. **`respond` 与 `file_server` 写响应走的是不同的路** ——
   [DSL 参考](../docs/architecture/dsl-reference.md)：`encode` 今天只接在
   `file_server` 与转发那两处。⇒ 两个变体**都不配 `encode`**，且 payload 不可压缩
   ⇒ 这一格对两边都不起作用。
2. **它的 payload 与「静态吞吐」那一类不是同一份字节** —— `respond` 的正文
   **只有内联形态**（⛔ 没有 file 形式）⇒ 必须可打印，取的是 base64 字母表，
   而静态吞吐那一类取的是 `/dev/urandom`。
   ⇒ ⛔ **不许**把 `diag/` 的读数与 `raw/static-throughput/fulcrum.json` 并排比；
   本步比的是**同一趟里的两个变体**，两边用的是同一份可打印字节。

### `cache-hit-p99` 的口径（`G150` ②）

**拓扑**：一个 `file_server` 源站 + 两个带 `cache` 的反代变体，**一次只起一个变体**。
★ 源站是必须的：`crates/fulcrum-server/src/lib.rs:654` 写着「缓存**只裹
`reverse_proxy`**」⇒ ⛔ 不能把 `cache` 挂在 `file_server` 上省掉这一层。
⚠ 命中之后源站根本不被访问 ⇒ 它在测量窗口里的成本 ≈ 0。

**为什么必须背靠背**：缓存后端是**进程级**的，多个 `cache` 块写不同的 `disk`
（含「一个写了、一个没写」）是编译期错误 `FUL-DSL-0035` ⇒ 两个后端不可能共存于一个进程。
★ 内存那份配置由磁盘那份**删掉 `disk` 一行派生**，⛔ 不是另写一份。
⚠ 两处差别如实写在脚本头部：`disk` 那一行（被测变量）与监听端口（机械必需）。

**`ttl` 由 `BENCH_DURATION` 算出来（10 倍），⛔ 不是字面量** —— 两处会飘的值，
飘掉的那天没有任何东西会说，而症状是「量到的其实是重验证」。

**⚠ ⚠ 阈值有意不定**（`G150` ② 明写）：定一个没有实测支撑的数字正是 `G148` ③
点名的那种错。本步只把数量出来，阈值等有数之后再定。

**这一格的判据长什么样，以及它们是怎么被证出来的**（2026-09-09 实测，四条反证）：

| # | 注入 | 实测 |
|---|---|---|
| ① | 输出改落 `raw/` | `C17` 与 `C18` **各红一条**（前者：`raw/` 类别数 1→2；后者：`diag/` 下产物为 0）|
| ② | `disk` 指向不可用目录 | `✗ cache-disk（开跑前）X-Fulcrum-Cache 该是 'HIT-DISK'，实际 '（这个头根本没出现）'`；⚠ **同趟内存臂四项全过** ⇒ 单变量。★ 这条由 diag 脚本自己拦下，门禁在步骤 A 就中止，**没走到 C18** |
| ③ | `ttl` < `BENCH_DURATION` | ⛔ ⛔ **第一版判据在这个注入下全绿** —— 见下 |
| ④ | 删掉 `SNAP_CACHE_FS` 那次 export | `✗ C19 这几格没被记进去：fs`，另两格照旧 ⇒ 那一格真的来自探测 |

⛔ ⛔ **③ 那条必须读完**：本步原先写的是「跑完后再核一次 `X-Fulcrum-Cache`，
与开跑前相同 ⇒ 整趟没重验证」。**那是错的**，`ttl=1s` < `duration=2s` 的注入下
整个门禁**照样全绿**。★ 根因：`CacheState` 只有 `Hit` / `Revalidated` 两个值
（`cache/mod.rs:261`），而**重验证之后条目重新变新鲜** ⇒ 之后的请求又是 `Hit`，
与「从未过期」在最终那一次观测上**完全相同**。
⇒ 改判 **`Age`**：`Age = now − stored_at`（`lib.rs:1384`），而重验证走
`refresh(…, now_unix(), …)` → `stored_at = now`（`cache/store.rs:208`）⇒ **`Age` 归零**。
判据是**跑完后 `Age` ≥ 负载时长**（预热在负载之前 ⇒ 没被刷新的话只会更大）。
同一注入下新判据**当场红**。
★ 这是 `G148` ③ 那一族的又一例：**判据看着正经，但量纲挑错了** ——
⚠ 而它是被**反证**抓出来的，⛔ 不是读代码读出来的。

**观测值落进原始数据，⛔ 不只打印**：`delta.json` 记 `cache_state`
（每个变体 `before` / `after` 各一组 `{state, age}`）与 `duration_secs`，
由 `tests/bench/gate.sh` 的 **C18** 独立复核。
★ 起因同样是实测：门禁把 `bench/run.sh` 的输出重定向进**容器里**的日志，
`--rm` 之后就没了 ⇒ 只打印等于没有证据。

**缓存根的文件系统**由 `env.json` 的 `cache_root` 三格记着（`path` / `fs` / `rwf_nowait`），
与 `site_root` 同形，由 **C19** 判它说不说得出话。
⚠ ⚠ **两条路上它不是同一种文件系统**：`bench/docker-run.sh`（合格宿主）挂 ext4 匿名卷；
而 `tests/bench/run.sh`（开发机门禁）不设 `BENCH_WWW_ROOT` ⇒ 落在 **overlay** 上
（实测 `{'path': '/tmp', 'fs': 'overlay', 'rwf_nowait': 'no'}`）。
⇒ ⛔ **两条路的读数不许并排比** —— 而现在原始数据自己说得出这件事。

```
  env.json                       环境快照 + 合格性判定（schema: fulcrum-bench-env/1）
  raw/<用例类>/<被测>.json        oha 的原始输出，原样落盘
  diag/<诊断步骤>/<变体>.json     诊断读数（⛔ 不参与判定，见上一节）
  verdict.txt                    判定结论，或「为什么不出结论」
```

★ `raw/` 下的东西是 G19 要求「全部公开」的那份**原始数据**。⛔ 不要在提交时
筛掉「不好看」的那几趟 —— 那样公开的就不是原始数据了。`diag/` 同理。

---

## ⛔ 这套东西证不了什么

- ⚠ **它给出的结论只有一类、只有一趟、只有一台机器**（2026-09-06 静态吞吐，见本页开头）。
  ⛔ 别把那一格读成 M3 的整体结论 —— §8 划了七类，这是第一类。
- ⛔ **它说不了枢衡为什么慢。** 那一趟只是读数，本目录不含任何根因结论。
- **它只跑「静态吞吐」一类。** §8 划了七类（静态吞吐 · 反代吞吐 · TLS 握手 ·
  L4 转发 · 缓存命中 · 长连接 · 高并发短连接），第一刀按 G132 只做一类 ×
  三家 —— 因为「该类最强者」这个概念还没被检验过，先铺覆盖面是在检验之前铺。
- **`tests/bench/run.sh` 全绿 ≠ 对拍达标。** 它判的是流水线活着、判据判得动。
- **合格性里那两件靠声明的事没有门**（专机 · 无 TUN 代理）。★ G145 把第三件
  （内核参数）从声明里拆出来变成了门，⛔ 但那**没有**让这两件也变得可验证。
- **判据 ④ 说不出压测端到底有没有饱和。** 承重的那一半（B 收敛）只回答「这组数
  不可比」，⛔ **它分不出是生成器到顶、环回到顶、还是 CPU 亲和没分开**。真正能直答
  这一问的是 A（绝对天花板），而 **A 今天没打开** —— 它要一个「确实比四家都快」的
  参照服务，那个选择在合格宿主到位之前验不了。⇒ 在 A 打开之前，「oha 没有先饱和」
  这句话**本套东西证不了**，它只能证「四家的数彼此分得开」。
- **`BENCH_MIN_SPREAD` / `BENCH_GEN_HEADROOM` 这两个阈值没有实测支撑**（见上一节）。
- **容器里读到的 sysctl 仍然不是宿主的** —— G145 没有改变这一点，它改变的是
  **我们不再假装那两者是一回事**：四个 per-netns 键改成在容器里设、在容器里判，
  宿主那一个在宿主上设、在宿主上判。快照把容器实测记成 `sysctl_as_seen_in_container`，
  把两侧声明与宿主实测记成 `kernel_params`，⇒ 第三方可以自己重算那次比较。
  ⚠ ⛔ 但它**证不了宿主上那个值在整趟对拍期间没被改过** —— 启动器只在开跑前读一次。
- **`netdev_max_backlog` 那道门证不了 16384 就够用。** ★ 够不够是可以量的：
  `/proc/net/softnet_stat` 第 2 列就是这一项的丢包数（实测它是全局的，容器里读到的
  就是宿主的）⇒ **对拍前后各读一次**才是那个判据，⛔ 而本套东西今天还没有自动读它。
