# 這份資料裡被改過的兩處

> 本目錄的原始資料與從宿主取回的原件逐位元組相同，**只有兩處例外**：① `env.json` 的 `attest`
> 去標識（下面前幾節）；② 兩份 `oha-request.txt` 的行尾 CRLF → LF（最後一節）。
> 兩處都機械核過，⛔ 沒有第三處。

## ① `attest` 去標識

> ★ 本儲存庫是公開倉。`env.json` 裡的 `attest` 是**人寫下來的宣告原文**，快照按設計把它
> 逐字記下來。這一趟那句原文同樣點名了**其它專案**的服務 ⇒ 按 owner 2026-09-06
> 定下、2026-09-10 視窗二沿用的同一條規則處理：**入庫，但宣告改成不點名**，並把改了什麼明寫在這裡。
>
> ⛔ **不靜默改。** 一份被悄悄修飾過的記錄，與一份編造的記錄無法區分。

### 改了什麼

本目錄有**兩份** `env.json`（[`env.json`](env.json) 與 [`ws-off/env.json`](ws-off/env.json)，兩趟用的是
同一句宣告），兩份做的是逐字相同的改動：

| | |
|---|---|
| 欄位 | `env.json` → `attest` |
| 其餘欄位 | ⛔ **一個字都沒動**（含 `qualified` / `disqualifiers` / `load_params` / 全部讀數；`raw/` 與 `diag/` 下的原始資料只有 ② 那一處行尾例外） |
| 標記 | `env.json` 末尾追加了 `"attest_redacted": true` ⇒ 機器讀得出來這份宣告被改過 |
| 做法 | **文字替換恰好那一行**，再在末尾追加那一個鍵（上一行的 `}` 因此多了一個逗號）。⛔ 沒有重新序列化 —— 那會讓別的欄位的位元組（鍵序、縮進、轉義）跟著變，上一行那句「一個字都沒動」就不成立了 |

**入庫的這一版**（與兩份 `env.json` 裡逐字相同）：

```text
专机：该机上全部应用服务与数据存储（共 6 个） 已全部停止（owner 2026-10-05 授权）· 无 TUN：网络设备只有 lo/eth0/docker0（docker0 是容器桥，非代理）· 仍在跑：一个出站隧道客户端、云厂商的两个探针、系统基础服务（chrony/cron/rsyslog/tuned/unattended-upgrades/fwupd/ModemManager/udisks2/multipathd）—— 它们仍会偶尔占用 CPU
```

**與執行環境實際宣告的那一版相比，差別只有「具名 → 計數／角色」這一類，共三處：**

| 執行環境原文 | 入庫版 |
|---|---|
| 被停掉的 6 個服務，逐個具名 | 該機上全部應用服務與資料儲存（共 6 個） |
| 一個隧道用戶端，具名 | 一個出站隧道用戶端 |
| 兩個雲廠商探針，具名 | 雲廠商的兩個探針 |

★ **這句是機械核過的，⛔ 不是自述**：對原文依次做這三處替換，結果與入庫版**逐字相等**；
解析兩份 JSON，除 `attest` 與新增的 `attest_redacted` 外每個欄位的值都相等；按行比，變了的只有
`attest` 那一行與末尾那三行。去標識後對整個目錄掃他專案名 / IP / 主機名，零命中。
完整原文留在本機執行記錄裡，⛔ 不入公開倉。

### ★ 與視窗二那份宣告的兩處差別（都是照實寫，⛔ 不是措辭調整）

- 「仍在跑」的系統基礎服務多列了 `fwupd/ModemManager/udisks2/multipathd` —— 它們是發行版常駐服務，
  本趟停服前逐個看過執行中的 unit，照實列進來。
- 雲廠商探針：停服前核到其中一個探針的 systemd unit 報 `inactive`、它的處理程序卻在跑 ⇒ 宣告按**處理程序**寫。
  入庫版裡兩者都歸成「雲廠商的兩個探針」，與視窗二同一種寫法。

### ★ 為什麼這樣改不削弱這句宣告

`attest` 那一格要回答的是「**這臺機器有沒有在承載真業務**」。它的資訊量在於
「有幾個、停沒停、還剩什麼在跑」—— 這三件在入庫版裡一件都沒少。
被去掉的是**誰**在跑，而那與這句宣告的強度無關。

### ⚠ 這份宣告仍然只有紀律，沒有門

「專機」與「無 TUN 代理」兩件**仍然是容器原理上看不見的**（G145 只把核心參數那件拆成了門）。
⛔ **宣告不是證明**，能做到的只有「誰都沒宣告過就一定不算合格」。

## ② 兩份 `oha-request.txt` 的行尾 CRLF → LF

| | |
|---|---|
| 檔案 | [`raw/short-connection-throughput/oha-request.txt`](raw/short-connection-throughput/oha-request.txt) 與 [`ws-off/` 下同名那份](ws-off/raw/short-connection-throughput/oha-request.txt) |
| 原件 | 用例指令碼把 oha 發出的請求**原樣**寫入磁碟（合成伺服器端抓的），HTTP 的行尾就是 CRLF —— 每份 7 個 CR，**全部**成對出現在 CRLF 裡 |
| 入庫版 | 每個 CRLF 換成 LF，⛔ 別的位元組一個沒動：入庫版 = 原件刪掉全部 CR，逐位元組相等（機械核過） |
| 為什麼 | 本儲存庫 `.gitattributes` 是 `* text=auto eol=lf`，原樣提交會在索引裡被轉成 LF、而工作樹仍是 CRLF ⇒ 門禁的行尾檢查（`git ls-files --eol`，工作樹 `w/crlf` 即紅）當場紅。owner 2026-10-05 在「轉 LF 並寫明」「保留位元組、改門禁」「不入庫」三條裡選了第一條 |
| 不影響判定 | 視窗清單 8d 用的 `bench_request_close_violations`（`bench/lib.sh`）自己先刪 `\r` 再判；對入庫版重跑一次，照樣什麼都不打（= 請求裡帶著 `Connection: close`） |

CRLF 的原件留在本機執行記錄裡。
