# 这份数据里被改过的两处

> 本目录的原始数据与从宿主取回的原件逐字节相同，**只有两处例外**：① `env.json` 的 `attest`
> 去标识（下面前几节）；② 两份 `oha-request.txt` 的行尾 CRLF → LF（最后一节）。
> 两处都机械核过，⛔ 没有第三处。

## ① `attest` 去标识

> ★ 本仓是公开仓。`env.json` 里的 `attest` 是**人写下来的声明原文**，快照按设计把它
> 逐字记下来。这一趟那句原文同样点名了**其它项目**的服务 ⇒ 按 owner 2026-09-06
> 定下、2026-09-10 窗口二沿用的同一条规则处理：**入库，但声明改成不点名**，并把改了什么明写在这里。
>
> ⛔ **不静默改。** 一份被悄悄修饰过的记录，与一份编造的记录无法区分。

### 改了什么

本目录有**两份** `env.json`（[`env.json`](env.json) 与 [`ws-off/env.json`](ws-off/env.json)，两趟用的是
同一句声明），两份做的是逐字相同的改动：

| | |
|---|---|
| 字段 | `env.json` → `attest` |
| 其余字段 | ⛔ **一个字都没动**（含 `qualified` / `disqualifiers` / `load_params` / 全部读数；`raw/` 与 `diag/` 下的原始数据只有 ② 那一处行尾例外） |
| 标记 | `env.json` 末尾追加了 `"attest_redacted": true` ⇒ 机器读得出来这份声明被改过 |
| 做法 | **文本替换恰好那一行**，再在末尾追加那一个键（上一行的 `}` 因此多了一个逗号）。⛔ 没有重新序列化 —— 那会让别的字段的字节（键序、缩进、转义）跟着变，上一行那句「一个字都没动」就不成立了 |

**入库的这一版**（与两份 `env.json` 里逐字相同）：

```text
专机：该机上全部应用服务与数据存储（共 6 个） 已全部停止（owner 2026-10-05 授权）· 无 TUN：网络设备只有 lo/eth0/docker0（docker0 是容器桥，非代理）· 仍在跑：一个出站隧道客户端、云厂商的两个探针、系统基础服务（chrony/cron/rsyslog/tuned/unattended-upgrades/fwupd/ModemManager/udisks2/multipathd）—— 它们仍会偶尔占用 CPU
```

**与运行时实际声明的那一版相比，差别只有「具名 → 计数／角色」这一类，共三处：**

| 运行时原文 | 入库版 |
|---|---|
| 被停掉的 6 个服务，逐个具名 | 该机上全部应用服务与数据存储（共 6 个） |
| 一个隧道客户端，具名 | 一个出站隧道客户端 |
| 两个云厂商探针，具名 | 云厂商的两个探针 |

★ **这句是机械核过的，⛔ 不是自述**：对原文依次做这三处替换，结果与入库版**逐字相等**；
解析两份 JSON，除 `attest` 与新增的 `attest_redacted` 外每个字段的值都相等；按行比，变了的只有
`attest` 那一行与末尾那三行。去标识后对整个目录扫他项目名 / IP / 主机名，零命中。
完整原文留在本地运行记录里，⛔ 不入公开仓。

### ★ 与窗口二那份声明的两处差别（都是照实写，⛔ 不是措辞调整）

- 「仍在跑」的系统基础服务多列了 `fwupd/ModemManager/udisks2/multipathd` —— 它们是发行版常驻服务，
  本趟停服前逐个看过运行中的 unit，照实列进来。
- 云厂商探针：停服前核到其中一个探针的 systemd unit 报 `inactive`、它的进程却在跑 ⇒ 声明按**进程**写。
  入库版里两者都归成「云厂商的两个探针」，与窗口二同一种写法。

### ★ 为什么这样改不削弱这句声明

`attest` 那一格要回答的是「**这台机器有没有在承载真业务**」。它的信息量在于
「有几个、停没停、还剩什么在跑」—— 这三件在入库版里一件都没少。
被去掉的是**谁**在跑，而那与这句声明的强度无关。

### ⚠ 这份声明仍然只有纪律，没有门

「专机」与「无 TUN 代理」两件**仍然是容器原理上看不见的**（G145 只把内核参数那件拆成了门）。
⛔ **声明不是证明**，能做到的只有「谁都没声明过就一定不算合格」。

## ② 两份 `oha-request.txt` 的行尾 CRLF → LF

| | |
|---|---|
| 文件 | [`raw/short-connection-throughput/oha-request.txt`](raw/short-connection-throughput/oha-request.txt) 与 [`ws-off/` 下同名那份](ws-off/raw/short-connection-throughput/oha-request.txt) |
| 原件 | 用例脚本把 oha 发出的请求**原样**落盘（合成服务端抓的），HTTP 的行尾就是 CRLF —— 每份 7 个 CR，**全部**成对出现在 CRLF 里 |
| 入库版 | 每个 CRLF 换成 LF，⛔ 别的字节一个没动：入库版 = 原件删掉全部 CR，逐字节相等（机械核过） |
| 为什么 | 本仓 `.gitattributes` 是 `* text=auto eol=lf`，原样提交会在索引里被转成 LF、而工作树仍是 CRLF ⇒ 门禁的行尾检查（`git ls-files --eol`，工作树 `w/crlf` 即红）当场红。owner 2026-10-05 在「转 LF 并写明」「保留字节、改门禁」「不入库」三条里选了第一条 |
| 不影响判定 | 窗口清单 8d 用的 `bench_request_close_violations`（`bench/lib.sh`）自己先删 `\r` 再判；对入库版重跑一次，照样什么都不打（= 请求里带着 `Connection: close`） |

CRLF 的原件留在本地运行记录里。
