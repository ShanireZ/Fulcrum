# 三层，方向单一

```text
DSL（Caddyfile 式，人写）
        │  编译
        ▼
结构化配置（唯一内部事实；机器、UI、自动化直接写这一层）
        │  校验 + 装载
        ▼
运行时对象图（路由表、上游池、TLS 解析器、缓存句柄）
```

- **两个入口都合法**：人写 DSL，机器写结构化配置。★ **DSL 是结构化配置的一个前端，不是它的替代。**
- **diff、版本化、原子回滚全部建在结构化层。** DSL 因此可以自由演进而不动内核。
- ★ **不做反向生成**（结构化 → DSL）。注释、缩进、简写形式在往返中**必然丢失**，投入产出比不成立。

# 结构化那一层是 **JSON**（G48）

★ **这一项此前是规格真空**——G11 把 diff、版本化、原子回滚全建在结构化层上，
却从没有一处文档写过它是什么格式。由 **G48** 定为 **JSON**：
机器写、diff 稳定、类型无歧义、无缩进陷阱，且 **load API 与磁盘上那份是同一种格式**，
不需要两套编解码。未选 YAML 是因为隐式类型转换（`no` → `false`）与缩进噪音**恰好打在
diff 与原子回滚这两件事上**；未选 TOML 是因为路由树是深嵌套 + 数组套表，机器生成的产物最难读。

⚠ **别和 `conf/*.yaml` 搞混**：那是 **Pingora 自己的 `ServerConf`**，不是枢衡的配置层。
M1 之后它由枢衡的结构化配置生成，不由人手写。

# DSL 的四条已定语义

✅ **D3 已结案**（G60–G63）。**完整指令清单见 [DSL 指令集参考](/architecture/dsl-reference.md)**；本页只记语义层面的四条：

| | 决策 | 一句话 |
|---|---|---|
| 执行顺序 | ★ **G49** | 站点块内按**内建顺序表**执行，**不是书写顺序**（照 Caddy）。★ owner 推翻了 AI 的「书写顺序即执行顺序」 |
| 匹配器 | **G50** | 复杂条件走 `@name { ... }` 命名块；行内**只允许路径** |
| 报错 | **G51** | 一次报全 + 行列号 + 源码片段 + caret + **稳定错误码**（`FUL-DSL-0007` 形） |
| 未实现能力 | **G47 / G52** | **隐式回落**（DSL 里不写 `fallback`），但**装载日志逐条列出**走了回落的路由 |

## ★ ★ G49 的代价必须一起落实，否则它会长成自己批评的那个东西

内建顺序表换来「用户随便写也能跑对」与「Caddyfile 迁移零意外」，代价是
**书写顺序 ≠ 执行顺序**。四条配套缺一不可：

1. **顺序表是公开契约**，与 DSL 参考文档同级维护，不能只活在代码里。
2. **必须有保序逃生口**（`route` 块内按书写顺序执行）。
3. ★ ★ ★ **新增指令必须在表里有位置，否则编译不过。** 这是最容易烂掉的一处：
   若按「不在表里就排最后」处理，新指令会**悄悄跑在错误的位置上**，
   而没有任何一行输出会说出来。**做成编译期穷尽性检查，不是注释提醒。**
   ★ Caddy 自己就是这么做的：不在 order 列表里的指令直接报错。
4. **错误提示要能解释位置**：执行顺序与书写顺序不同而出了意外时，
   诊断必须说出「它实际跑在哪一步、为什么」，否则用户只能去背那张表。

# DSL 形状（示意）

```text
example.com {
    reverse_proxy 127.0.0.1:3000
}

api.example.com {
    reverse_proxy 10.0.0.1:8080 10.0.0.2:8080 {
        lb_policy      least_conn
        health_uri     /health
        health_interval 5s
    }
}
```

# ★ 为什么是 Caddyfile 式而不是 nginx 式（G20）

未采纳 nginx 式语法的理由值得记住，它不是审美判断：

> **看起来一样但语义不同，比完全不同更危险**——用户会带着旧假设一路踩坑。

nginx DSL 被点名的两个坑（`PLAN.md` §3）：`if` 不可靠、`location` 匹配顺序反直觉。**照抄它的形状就会把这些期待一起继承过来。**

# 最容易在哪做错

0. ★ ★ ★ **给顺序表加一个指令，却没给它在表里安排位置。** G49 之下这不是小疏忽：不在表里的指令若被「默认排最后」接住，就会**悄悄跑在错误的位置上**，而配置能装载、请求能通、日志一行不报。这与本项目反复抓到的「声明了却没人接」是同一个形状，处置也一样——**做成编译期穷尽性检查，让它编不过**。
1. ★ **把 DSL 当成唯一入口。** 机器写的是结构化配置那一层；如果只给 DSL 加了某个能力而结构化层没有，自动化就用不上它。
2. ★ **把 diff / 回滚建在 DSL 文本上。** 那样注释与格式变化会被当成配置变更，而真正的语义变更可能被格式化掩盖。**它们必须建在结构化层。**
3. **试图做反向生成。** 每隔一段时间就会有人提议它，理由通常是「让 UI 能改配置再写回 DSL」——但 G23 首版不做 UI，而机器本来就该直接写结构化层。
