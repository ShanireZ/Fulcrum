★ **完整表述在 [`PLAN.md`](../../PLAN.md) §4。** 这里只补每条**怎么用来否决一个设计**。

| | 原则 | 拿它否决什么 |
|---|---|---|
| 1 | **一个进程，一份配置，一套观测** | 任何让用户「再装一个东西」的设计。★ 这是产品的**全部理由**——[定位](/product/positioning.md) 里那个狭窄空位就建在它上面 |
| 2 | **吸收长处，不继承短处** | 任何「三家都这么做」但说不清避开了哪个坑的抄袭。`PLAN.md` §3 的长短处表是检查表 |
| 3 | **期望状态是唯一权威，例外必须可见** | 第二条持久化写路径；不出现在 stats 里的隐式状态 → [管理面](/architecture/control-plane.md) |
| 4 | **先验证，再发布；失败即回滚** | 把配置变更当成文件写入而不是事务的实现 |
| 5 | **默认即安全** | 默认出机器的管理面；不要求显式准入就能启用的危险能力 → [安全基线](/platform/security-baseline.md) |
| 6 | **性能以端到端实测为准，且数据公开** | ★ 任何「快 N 倍」式表述；任何无法复现的性能声明 → [性能验收标准](/verification/performance-bar.md) |
| 7 | **回落是脚手架不是架构** | 任何让回落层长大的改动 → [回落层](/architecture/fallback.md) |

# ★ 第七条的判据最特别

> **它的成功标志是被删除。**

这句话把回落层从「一个模块」变成了「一段有终点的工期」。判据因此是可操作的：**如果一个改动让回落层更难删，它就违反了第七条**——哪怕那个改动本身让回落工作得更好。

能力翻译、配置语义映射、统一两家的行为差异，全部因此出局。

# ★ 第三条与第六条是本项目最容易被违反的两条

- **第三条**：加一个「顺手持久化一下」的写路径太容易了，而 G18 的整个判据就是**丢得无声无息比丢本身更糟**。
- **第六条**：性能数字是最容易脱口而出的东西。[工作方式](/governance/working-agreement.md) 把它单列成一条纪律，`AGENTS.md` 里也写了一遍。
