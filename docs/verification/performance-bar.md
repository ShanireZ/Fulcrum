# 四条

| | 口径 |
|---|---|
| **对象** | Caddy、HAProxy、Nginx **三家全部对拍**，★ **不挑软柿子** |
| **方法** | 同一台机、同一组用例、同一负载生成器 |
| **门槛** | 每类用例，枢衡**不劣于该类最强者** 10% |
| **公开** | 基准脚本与**原始数据**全部公开 |

★ **不发布无法复现的性能声明，不使用「快 N 倍」式表述。**

# 用例按类划分

静态吞吐 · 反代吞吐 · TLS 握手 · L4 转发 · 缓存命中 · 长连接 · 高并发短连接

★ **「该类最强者」逐类算，不是取三家平均、也不是取某一家当基准。** 静态那一类比的是 nginx，L4 那一类比的是 HAProxy——**枢衡要在每一格都追上那一格的冠军。**

# ★ 为什么这条标准这么严

因为 [定位](/product/positioning.md) 的整个论证建立在「三家的长处不冲突，可以收进一个实现」上。

**如果某一类明显落后，那个假设在这一类上就是错的**——而含糊的对拍会让这个错误一直藏着。逐类设门就是把假设拆成七个可证伪的命题。

# 环境必须可复现

`PLAN.md` §9 把「基准环境不可复现，数字失去意义」列为风险。缓解：

- 基准环境**用脚本固化**，含**内核参数与 CPU 亲和**
- 每次对拍**记录完整环境快照**

★ G26 的一个附带收益正在这里：Docker 环境**将来直接就是 CI 与对拍环境的底座**。见 [构建与验证](/platform/build-and-test.md)。

# 这条纪律不只在 M3 生效

[工作方式](/governance/working-agreement.md) 把它列为常驻纪律：

> ★ **绝不在没有可复现的端到端实测时宣称性能。**

[`AGENTS.md`](../../AGENTS.md) 也写了一遍。这意味着**在 M3 之前，任何性能表述都不该出现在文档、提交信息或对外材料里**——包括「应该会更快」这种。

# 与依赖升级的关系

G29 第 5 条：**每次升级必须通过当前里程碑的全部验证**。

★ **M3 之后，这句话的意思是每次依赖升级都要跑全量对拍**，不只是跑测试。见 [依赖策略](/platform/dependency-policy.md)。
