**Title**

```
Avoid initializing header slots and allocating header refs in read_request()
```

**Base**: `cloudflare/pingora` `main` · **Head**: `ShanireZ/pingora` `read-request-slots`

---

**Body**

Refs #<ISSUE_NUMBER>

Two commits, each with its own tests. Each also applies to `main` without the other, so either can
be taken alone.

1. **Parse request headers into uninitialized header slots.** `read_request()` no longer builds
   `[httparse::EMPTY_HEADER; MAX_HEADERS]` (8 KiB on 64-bit targets) before every parse attempt; it
   parses with `Request::parse_with_uninit_headers()` into `MaybeUninit` slots instead. The
   `patched_http1` path keeps initialized slots for `parse_unchecked()`.
2. **Keep request header refs on the stack instead of in a Vec.** The header offsets go into
   `[MaybeUninit<KVRef>; MAX_HEADERS]` through `populate_header_refs()`, a sibling of
   `populate_headers()` that applies the same rule (unnamed entries are skipped) and returns the
   slots it wrote. This removes one heap allocation per request that has headers. It adds one
   `unsafe` block, the cast of the initialized prefix, with a `SAFETY` comment.

### Why behavior does not change

- (1) In httparse 1.10.1, `Request::parse()` is `parse_with_config(buf, &Default::default())`,
  which calls `parse_with_config_and_uninit_headers()`; `parse_with_uninit_headers()` calls the
  same function with the same default config. The only difference is what `req.headers` holds when
  the result is not `Complete` (the original slots vs. the empty slice from `Request::new(&mut [])`),
  and `read_request()` only reads `req` on `Complete`.
- (2) The same offsets are computed by the same loop; only where they are stored changes. The loop
  that appends the headers is untouched (`header_refs` is now a `&[KVRef]`).
- The `read_request()` future does not grow: both arrays live inside the parse loop and are not
  held across an `.await` (`size_of_val` of the future is 216 bytes before and after on x86_64).
  The stack frame of the parse does grow by the `KVRef` slots (8 KiB).

### Tests

- `tests_stream::read_max_headers` (server.rs, commit 1): exactly `MAX_HEADERS` headers all come
  back with the right values, so every slot of both arrays is used; `MAX_HEADERS + 1` is still
  rejected with `InvalidHTTPHeader`. It guards equivalence, not the saving, so it still passes with
  this commit's code change reverted; it fails if the parser is given one slot too few, or if the
  ref slots of commit 2 are one short.
- `test_populate_header_refs` and `test_populate_header_refs_too_few_slots` (common.rs, commit 2):
  the refs match `populate_headers()`, unnamed entries are skipped, and too few slots panic instead
  of writing out of bounds.
- `tests/read_request_allocations.rs` (commit 2): a counting global allocator, in its own test
  binary, counts the allocations `read_request()` makes for a simple three-header request on a
  current-thread runtime. It allows at most 8; with commit 2 reverted the count is 9 and it fails.
  The binary also checks that the allocator does count.

  second needs a one-line rebase: `parse_req_buffer(&mut req, &buf, &mut headers[..max_headers])`.
  The second commit does not touch those lines.
- `read_response()` in `client.rs` has the same two patterns; I left it alone to keep this small.
- For timings, the in-tree `h1_pipelining` bench (`h1_single_request`, `h1_pipelining/bodyless/*`)
  goes through this path. I haven't quoted numbers: my machine was too noisy for them to mean much.
- `parse_with_uninit_headers()` exists since httparse 1.5.0, below what `pingora-core` already
  needs (1.6.0, for `allow_obsolete_multiline_headers_in_responses()`). Inline `const` array
  initializers need Rust 1.79, below the 1.85 MSRV.
